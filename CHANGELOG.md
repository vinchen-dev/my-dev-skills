## 0.9.1 — 2026-10-20

- Fewer repeated reads, found by benchmarking 0.9.0 against 0.8.0 on the same three features: the plan session re-read the files the `dev-explorer` had just reported on, the build re-read the modules the plan's Approach already cites before its first test, the verifier ran the full suite twice in a pass whenever it added tests, and the reviewer ran tests the verifier had already run. `dev-plan` now opens code only around a search hit the explorer's report does not list, cites the report's `file:line`, and asks the explorer a follow-up instead of reading; `dev-build` reads a task's files by the plan's cited ranges in one or two batched calls and treats the Approach as the design; `dev-verify` runs the suite once in the gates and only the added files afterwards; the `dev-reviewer` never runs tests.
- `dev-build` never schedules a wakeup or timer while the verifier and reviewer run: one fired after a finished build and re-entered dev-build on top of its report. Their completion notices are the signal.
- Plans stay near the 150-line limit: the Approach states the design and the order of writes and points at the Test strategy row that carries each check's status and message instead of restating them, since the build and every verifier and reviewer pass read the whole plan.

## 0.8.0 — 2026-10-15

- New skill `dev-commit-pr`, invoked with `/dev-commit-pr`: writes commit messages and the PR title and body for finished work in the repo's commit format with the ticket id, as GitHub Markdown with Summary, Changes, Testing, Deploy notes and Out of scope, from verified facts only and with no AI attribution. It writes text and never commits or pushes. `dev-ship` now uses the same PR shape when Matt's `pr` skill is not installed.
- Matt's `setup-matt-pocock-skills` is no longer required. No skill stops when `docs/agents/issue-tracker.md` is missing: the spec is the path the user names or `.scratch/<feature-slug>/spec.md`, and the tracker file is read only when it exists and the spec is an issue. `dev-build` used to stop at preflight without it.
- The `dev-reviewer` narrowed its first pass whenever fix rounds had run before it, so a build whose first verify failed never had its whole change reviewed; found in a benchmark where both complex runs went through that path. The plan gains a `Reviewed:` line that `dev-build` writes after each review pass, and the reviewer covers the whole change while it says `none`, afterwards the fix rounds after the round it names. `dev-build` now runs the first review alongside the first verify, so the review no longer waits for a passing verify and both sets of findings are fixed in one round. From the second cycle both also cover the callers of what the fix changed, not only its files.
- From the same benchmark: `dev-plan` adds bad-input rows for every endpoint touched (wrong types, `null`, unknown ids, operator and dotted keys reaching a database update, from the standards' Must rules), an abuse row for every rule the spec enforces, and states the write order and the failure case when one request writes more than once; `dev-build` writes each fix test-first; `dev-verify` passes a row only when its test exercises the row's risky case, and runs each test file once, reading one output.
- `dev-plan` does the impact analysis up front. The `dev-explorer` lists every consumer of each function, field, response shape, schema, export, constant or message the task changes; the plan re-checks that list by searching the names itself, gives each consumer a task or a reason it is unaffected in the new Affected areas table (path, change, changed because, breaks without it, task), and states each new or changed path's failure cases and their handling. `dev-build` implements only: a consumer it meets that the plan does not list stops the build as a plan gap instead of being patched in place and found cycles later.
- Indexes join the performance checks. `docs/standards.md` gains a Must that a query's filter and sort fields are covered by a declared index, or the plan says why the collection stays small; the `dev-explorer` reports where the repo declares indexes and the indexes on each collection a task queries, so `dev-standards` and `dev-plan` work from declarations rather than stack knowledge; `dev-plan` names the index each new or changed query relies on and schedules the schema change when it is missing; the `dev-reviewer` checks new queries against the declared indexes, reading declarations only.
- Fewer turns in `dev-build`, from a scan of six benchmark runs where every turn re-read a 160k to 280k context: it says to start in a new session after `dev-plan` (the planning conversation was 55 to 63% of the build's tokens), a plan bookkeeping write never takes a turn of its own, Matt's `tdd` is loaded once and applied to every task, and the verifier and reviewer briefs carry nothing from the caller's own system prompt or `CLAUDE.md`. Same checks, gates and reports.
- `dev-plan` delegates the whole scan to the `dev-explorer` and waits for its report instead of exploring alongside it and re-reading the files the report cites (4 to 5M tokens per complex plan), then verifies the report with one search per changed name and reads code by line range. The per-name re-check stays mandatory. The `dev-explorer` groups independent reads into one message (its complex scan took 85 turns, 72 of them one call each). The `dev-verifier` starts a long gate in the background and waits for the tool's completion notice instead of polling its log, which was 15 to 30% of each verify's turns; when only waiting remains it waits in one bounded call per ten minutes.
- `dev-ship` reads only the sections of the plan, verify report, build report and spec its steps use, and takes the criteria counts from the build report's `Criteria:` line; it used to point at `verify-report.md`, which has no counts line. `dev-standards` verifies each command with its output redirected to a file and reads back the exit status and the tail, instead of carrying a whole test or build run through every later step. `dev-commit-pr` reads the diff without lockfiles, snapshots and protected generated paths; the stat still lists them. `dev-ticket-summary` keeps its worked example in `example.md`, read when unsure, instead of loading it on every invocation. The command guard echoes at most 200 characters of a blocked command instead of the whole of it.
- The `dev-reviewer` fetches in batches instead of one file per turn (its passes took 29 to 85 turns, each re-reading a 70k to 150k context), with a cap per call so a batch cannot truncate. Both it and `dev-verify` now take the change as `git diff <base>` plus untracked files: the old `<base>...HEAD` form is empty when work-in-progress commits are declined, so each pass improvised a diff and got the staged state right only by luck.
- The `dev-reviewer` walks every line the diff removes and checks what depended on it: a variable still declared but never read, an import nothing uses, a comment describing the removed behaviour, or code left without its branch. A leftover that still runs is must-fix.

## 0.7.0 — 2026-10-08

- `dev-verify`, from reviewing three verifier runs on a client repo: a build scope never puts a criterion out of scope when the built part already opens the path it guards, the open-path rule names both kinds (a new field an existing endpoint persists unchecked, and an existing field a new rule now constrains that an endpoint still writes) with the tracing step that finds them, and an open path no plan row covers is a Failures entry headed `Open path:` rather than an invented row; gates come from the root `AGENTS.md` plus the nearest one above each changed file, one row per package; the Base line is always the plan's base and the caller's words never narrow the change; the criteria table holds the plan's rows only, so the counts add up, and an earlier `verify-report.md` is not read until the new one is written; each status cell holds one template word, and a behavioural criterion backed only by reading code is unverified; a gate that crashes before reporting is `fail` with no result, capped at `INCOMPLETE`, with `test-one` on the affected test files as partial evidence; no sections beyond the template; verifier-written tests follow `docs/standards.md` over neighbouring files; rows a `Done so far:` line lists as remaining are out of scope, and that line now carries row numbers; the diff includes untracked files; and the returned summary keeps every entry on one line. `dev-ship` accepts a no-result gate the way it accepts unverified criteria.
- `dev-build`, from the same build: the round limit is checked before every fix round against a new `Fix rounds:` plan field that records each round's failure keys, survives a resumed build and stops the loop when a key repeats; the verifier's drift line and notes are read after every verify, fixed when a plan task covers the item and otherwise carried into the report; the `dev-reviewer` brief carries paths, scope and the code-review flag and nothing else; the report keeps every template heading with `- none` under empty ones; a mid-build request from the user enters through a plan task the user adds, recorded under `## Decisions during build`, and is not a fix round; a disputed finding backed by a verifier test names the test and no longer burns rounds; Still open names files no review pass has seen; a build with no plan stops and sends the user to `dev-plan` instead of building from the spec or a ticket; a ticket scopes a build, and because `to-tickets` writes behaviour rather than task numbers, preflight matches the ticket to the plan's tasks and rows, confirms the mapping and any unmatched checklist items with the user in one question, and records it in the plan's new `Tickets:` line; the plan says what each slice changes and how it is proven. `dev-ship` adds `Closes <ticket>` to the PR when the build was scoped by a tracker ticket, and `dev-plan` now says to run `to-tickets` with the plan in context or as its argument, since it never looks for the plan file. `dev-plan` and `dev-verify` now treat a spec that says "works like X" as defining every user-visible behaviour of X, with a plan row each, and the `dev-reviewer` checks every list of X's fields for the new one.
- The loop narrows after its first cycle. The first verify and review cover the whole change and must find everything; from the second round the verifier re-proves only the rows the fix round touched or that failed, carries the rest from the previous report, checks drift in the changed files only, and still runs every gate in full, while the `dev-reviewer` and `code-review` cover the fix round's diff. The plan's `Fix rounds:` line records each round's keys and changed files, and the verifier and reviewer narrow from that record, never from the brief.

## 0.5.0 — 2026-10-07

Hardening from the first real runs of the workflow on a client repo, and fixes from reviewing a dev-spec-explain run.

- `dev-build` hardened after a real run: preflight stops when `docs/agents/issue-tracker.md`, the `Commands` section of `AGENTS.md` or `docs/standards.md` is missing, instead of letting the verifier and reviewer improvise; it branches off any shared branch, not only the default one; it records the work-in-progress answer in the plan's new `WIP commits:` field and writes `build-report.md` beside the plan; it builds plan tasks, by number or group when scoped, never tickets, and marks a partly covered task with a `Done so far:` line; and it hands the verifier nothing but paths and scope, so no gate can be skipped on instruction. `dev-verify` never invents gate commands, keeps one row per criterion, and gains an `out of scope` status that `dev-build` counts.
- A path a change leaves unvalidated or unapproved where the spec requires either now fails verification and is must-fix in the round that opened it, whichever ticket owns the full fix. - `dev-spec-explain`, from reviewing a real run: a screenshot with no text beside it, such as a log entry under an empty heading, is spec content reported in its own group rather than a gap; and the item rule's own example no longer bundles separable checks, so the worked example now splits the approval section into four items, matching the rule it illustrates.

## 0.3.0 — 2026-10-06

A new skill, automatic version bumps, and fixes from a review of the skills against Matt Pocock's installed 1.2.3 release.

- `dev-build`'s no-subagents fallback names the seven review axes inline. It used to point at `agents/dev-reviewer.md`, which Codex installs don't include, and Codex is the case that fallback exists for. Its report template now collects suggestions from `code-review` as well as the `dev-reviewer`.
- `pr` is no longer listed among Matt's skills the installer depends on, since his 1.2.3 release doesn't ship it; `dev-ship` already falls back to its own PR structure. It goes back on the list when his release includes it.
- `dev-standards` no longer says his `implement` reads `docs/standards.md` (it doesn't; the `code-review` it calls does), and the standards template credits `dev-reviewer`, not `code-review`, with relying on its section headings.
- Version bumps are automatic. `.githooks/pre-commit` runs `npm run bump` on the first commit after a push, which bumps the patch number, regenerates the manifests, opens the next `CHANGELOG.md` section and dates the one that shipped; later commits in the same cycle leave it alone. Run `npm run bump minor` yourself when a batch changes behaviour; a second bump in one cycle relabels the section rather than stacking a version that never shipped. Enable in a clone with `git config core.hooksPath .githooks`.
- New skill `dev-spec-explain`: explains a feature spec in plain language for non-technical readers (product, QA, operations, support), with a list of affected features, then the changes grouped by feature (the configuration page, the approval page, the log) and split inside each group into small items a reader can check one at a time, with a Before/After table per feature for larger specs, on-screen labels, exact message text, what does not change and gaps in the spec. It reads whole documents and never reports code impact; that stays with `dev-plan` and `dev-explorer`. Model-invocable, with a worked example in `skills/dev-spec-explain/example.md`.

## 0.2.0 — 2026-10-05

The `npx` installer became a device-level installer instead of a wrapper around each tool's marketplace commands.

- `init` no longer registers this plugin with a marketplace. It installs onto the device: one real copy of the plugin, with each tool symlinked to it. Full parity (skills, agents, hooks) on Claude Code, verified against Claude Code 2.1.267; skills only on Codex via `~/.agents/skills`. Run each tool's own `plugin marketplace add` and `plugin install` for the marketplace route instead. The two put files in different places, so pick one.
- Run from a git clone, the clone itself is that one copy and both tools link straight at it, so edits are live with no reinstall. Any other way, `npx` included, it copies to `~/.agents/my-dev-skills` first, because npm deletes its cache after the run and a link into it would dangle. `--shared` and `--link` force either side, and `--link` no longer has to be typed from a clone.
- `init` asks which tools to install for: a checklist driven by arrow keys and space, pre-ticked with the tools whose CLI it found. It falls back to a typed prompt where raw mode isn't available, and asks nothing when piped or given `--claude`, `--codex` or `--yes`, so scripted runs are unaffected.
- `uninstall` removes only what the install recorded, so a run that chose one tool never disturbs the other. It previously acted on whichever CLIs happened to be present.
- Fixed: a refused uninstall deleted its install record anyway, leaving the links in place with nothing for a later uninstall to act on, so the install could not be removed. It now keeps the record, reports how many entries it left alone, and exits non-zero.
- `--help` finds the end of its own header comment rather than slicing a fixed line count, so editing that comment can no longer truncate the help or leak code into it.
- README covers both install routes, says plainly that they put files in different places, and gains an uninstall section with the verified commands for each.

## 0.1.0 — 2026-10-05

First release.

- Every skill carries a `dev-` prefix (`dev-standards`, `dev-plan`, `dev-verify`, `dev-build`, `dev-ship`). Flat skill directories like `~/.agents/skills` are a shared namespace, and bare names such as `plan` and `build` collide there; Codex ships a bundled skill named `plan`, and Claude Code ships one named `verify`. The prefix keeps all five distinct in both tools.

- Skills: `dev-standards` generates a repo's `AGENTS.md`, `CLAUDE.md` and `docs/standards.md` from evidence, with an update mode that never touches rules you wrote; `dev-plan` derives numbered acceptance criteria from the spec and maps each to a test, adding scale and failure rows when a change touches a data path; `dev-verify` runs the repo's gates and proves each plan row with evidence (named to stay clear of Claude Code's bundled `/verify`); `dev-build` runs each plan task with Matt Pocock's `tdd`, then verify and two review passes in fresh contexts, with fix rounds; `dev-ship` writes the commit, changelog entry and PR description and squashes dev-build's work-in-progress commits; `dev-ticket-summary` condenses a finished investigation into a ticket-ready summary to paste, invoked by you only.
- Agents: `dev-explorer` scans a codebase read-only for `dev-standards` and `dev-plan`, and consults a Graphify knowledge graph (`graphify-out/`) and an Obsidian project vault through `obsidian-recall` when either is present, treating what they return as prior context to verify against the code rather than as fact; `dev-verifier` runs `dev-verify` in isolation; `dev-reviewer` gives a second look at performance and resources, security, reliability, structure and tests after Matt's `code-review`.
- Hooks: a post-edit formatter runs the repo's `format-one` command and warns when that command itself can't run; a pre-Bash guard blocks force pushes, hard resets, `git checkout .` and `git restore .`, forced branch deletes, recursive deletes of root or home, SQL drops and truncates, package publishes and terraform apply. Every guard rule has cases in `hooks/guard-cases.txt`, run by `npm run test:guard`.
- Conventions: `dev-build` asks once before making any work-in-progress commit and skips `code-review` if declined; nothing the workflow writes carries AI attribution; specs come from Matt's `to-spec` through the repo's issue tracker; issue-tracked features use the slug `<issue-number>-<kebab-title>`.
- Standards template with universal defaults, source tags and a stack-pack format guide; `monorepos.md` for per-package `AGENTS.md`.
- Claude Code and Codex manifests and marketplace files generated from `package.json` by `npm run manifests`, which refuses metadata the tools would reject.
- `npx my-dev-skills` installer with `init`, `init --matt`, `init --link`, `uninstall` and `--dry-run`. It uses each tool's plugin commands (Claude Code, and Codex 0.145 with `plugin add` and `plugin remove`) when they're available. Otherwise, instead of copying separately into each tool, it copies this plugin once into a durable shared location, `~/.agents/my-dev-skills`, and symlinks Claude Code and Codex to that single copy, full parity (skills, agents, hooks) on Claude Code, verified against Claude Code 2.1.267, skills-only on Codex via `~/.agents/skills`; a later `init` refreshes the one copy for both tools. Falls back further to independent copies only if symlinks aren't possible at all. In every mode it refuses to overwrite or delete anything it didn't create, proven by the link target for a symlink and by a marker file for a copy. `--link` skips the copy step entirely and symlinks a live checkout straight in, for developing the plugin itself. Never installs Matt's skills on top of existing file copies.
- Depends by name on Matt Pocock's `mattpocock-skills` plugin, installed from his own marketplace rather than re-listed in this one: `grill-me`, `to-spec`, `to-tickets`, `tdd`, `code-review`, `diagnosing-bugs`, `setup-matt-pocock-skills`, and `pr` when present.
